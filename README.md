# Push Notification project

React admin dashboard, Express API, MySQL storage, and a WordPress integration for web push.

## Local setup

1. Start the **MySQL80** Windows service. It uses port 3306. XAMPP is a separate database installation; use the server containing your `push_notifications` database.
2. For a new installation, create the database and run `server/db/schema.sql` inside it. Existing databases need no migration for the WordPress changes.
3. Copy `server/.env.example` to `server/.env` only for a new installation. Configure the database credentials and administrator login. Generate `PUSH_API_SECRET` with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Keep this secret stable; changing it invalidates login sessions and sender API keys.
4. In `server`, run `npm.cmd install` and `npm.cmd run dev`.
5. In a second terminal, in `client`, run `npm.cmd install` and `npm.cmd start`. The dashboard opens at http://localhost:3000; the API uses http://localhost:5000.
6. Log in and select a domain. Existing browser sessions from before authenticated APIs were added must log in again.

## Live WordPress setup

1. Host the Node server on a public HTTPS address with access to MySQL. Deploy `server` together with `client/public` in their existing relative locations: the API serves its SDK, worker, and plugin ZIP from that public folder. From the repository root, the backend start command is `npm --prefix server start`. Configure `PUBLIC_API_BASE` to the public API address, set real administrator credentials, set a real contact email in `VAPID_SUBJECT` (for example `mailto:you@your-domain.com`), preserve `PUSH_API_SECRET`, and use `NODE_ENV=production`. Forward HTTPS requests through your hosting provider or reverse proxy to Node's `PORT`. This repository does not provision hosting or certificates.
2. Set `REACT_APP_API_BASE` in `client/.env` to that same API address and restart/rebuild the dashboard. This is the dashboard-to-API address; `PUBLIC_API_BASE` controls the installation settings given to WordPress.
3. In Configuration, expand **Install WordPress Plugin** and download the ZIP. In WordPress, use **Plugins → Add New Plugin → Upload Plugin**, then activate it. If the plugin is already installed, replace it with this updated ZIP.
4. Open WordPress **Settings → Push Notifications**. Copy API Base, Service URL, Domain Key, VAPID Public Key, and Sender API Key from the dashboard. Leave Service Worker Path empty to use the worker bundled in the plugin. The sender key is for WordPress server requests only and is never injected into visitor scripts.
5. Save settings. Visit the registered website in a browser, click **Enable notifications**, and allow notifications. Both apex and `www` versions are accepted by the API; each browser origin has its own subscription.
6. Send a test from WordPress settings or the dashboard. Tests from Configuration target **all subscribers of that domain**; the dedicated push composer also supports audience filters. Results report acceptance by push services, not confirmed device delivery. Expired endpoints (404/410) are removed. With zero subscribers, the result explains that nothing was sent.
7. Optionally enable **Send on publish** in WordPress. New public, non-password-protected blog posts trigger a send. Existing published posts are not resent on every edit.

Install the WordPress plugin alone: it loads the SDK and serves the worker automatically. The alternative script method is for manually managed websites: add the snippet to the page head and host `push-sw.js` on that website.

Configuration uses a separate website/public-key summary and expandable **Install With Script** / **Install WordPress Plugin** rows. Both rows start collapsed and only one opens at a time. The script contains public configuration only; the administrator sender key stays in the WordPress setup panel, masked until revealed or copied. Copy buttons and downloads use the selected website's integration settings. Configuration retains its test form at `#send-push`; overview Send Push shortcuts open the dedicated composer. Popup, feedback, and native-app tabs are disabled until those integrations are implemented.

The default API address is local. It cannot serve visitors on a live WordPress site. The dashboard displays a local-setup notice until an HTTPS address is configured. A URL setting alone does not deploy the server.

Domain cards show **Configured** when the domain has its push keys and at least one saved browser subscription with encryption keys for that same domain and owner. This also recognizes existing imported subscriptions. This installation indicator is separate from the legacy domain verification status; it does not claim ownership verification or confirmed notification delivery.

## Domain management

Open **Manage domains** from the overview, or visit `/settings/domains`, for a table of saved websites. **New** opens the existing setup form at `/settings/domain`. **Edit** changes the friendly name; the registered hostname and push keys remain unchanged. To use a different hostname, create a separate domain. Select individual rows or use the header checkbox, then **Delete** to remove those domains and their stored subscriptions. Deletion requires confirmation and removes each domain with its subscriptions in one database transaction; failed rows remain selected for retry.

The API adds a nullable `domains.display_name` column automatically on startup if it is missing. Existing rows fall back to their hostname until renamed; new domain names are saved from the setup form. No domains or keys are regenerated. This additive migration runs after the deployment backup and supports older app images during rollback. The database account needs `ALTER` permission for this first startup. For a fresh database, import the baseline `server/db/schema.sql` and start the API to apply this addition. Normal database dumps include the new column and its values.

## Website overview

Click a domain card or its arrow to open `/dashboard?domain=DOMAIN_KEY`. The overview includes current subscriber totals, quick links, an audience country map, reporting status, and available events. **Send Push** opens the dedicated three-step composer for that website. Configuration and the website selector remain available from the overview, and **Refresh data** reloads its counts and map.

The authenticated `/api/domains/:key/overview` endpoint counts saved subscriptions with encryption keys for the selected domain and owner. Total and web counts include desktop and mobile browsers. Mobile browser counts use recorded device categories; native-app counts remain unavailable. Unknown device categories are reported separately. Counts describe subscriptions rather than unique people or lifetime registrations. Campaign history, delivery/click tracking, templates, and popup events are not enabled. Earlier test sends have no saved campaign history.

The Audience panel uses authenticated `GET /api/domains/:key/audience` country aggregates, with teal shading, country labels, and zoom/pan/reset controls. **View All** opens `/analytics?domain=DOMAIN_KEY` in a new tab using the existing browser login, while the dashboard stays open. Unknown locations stay gray and appear separately in the Analytics country table. Country rows include only that website and owner's saved subscriptions with encryption keys. Expired-subscription removal automatically changes these counts.

Startup adds nullable `subscriptions.country_code CHAR(2)`, `region_name VARCHAR(128)`, `region_code VARCHAR(16)`, and `city_name VARCHAR(128)` storage. Old rows stay unknown until their browsers revisit and the SDK resaves the subscription. New/resaved subscriptions take approximate locations from trusted Cloudflare headers; no visitor IP, precise coordinates, or GPS permission is added. Missing location data preserves previously recorded details, while changes in country or state clear incompatible older details. VPNs/proxies can affect estimates.

For state and city capture, select the API's zone (`micetraveladvisor.com`) in Cloudflare, open **Rules → Settings → Managed Transforms**, and enable **Add visitor location headers** ([official instructions](https://developers.cloudflare.com/rules/transform/managed-transforms/configure/)). This supplies `CF-Region`, `CF-Region-Code`, and `CF-IPCity` to the proxied API. Visit the website in an already-subscribed browser, then click **Refresh data** in Analytics. No plugin reinstall is needed. Existing countries cannot reconstruct missing state or city details.

The country-header policy accepts a direct Cloudflare edge peer or one Cloudflare IP in `X-Forwarded-For` from the existing local Caddy proxy. The API port must remain published to host loopback, and Caddy must continue overwriting incoming forwarding headers with its connecting peer, as [Caddy does by default](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults). Arbitrary forwarding chains, request-body country values, and unknown/Tor country codes are ignored. The Cloudflare edge CIDRs in `server/audience.js` were checked against [Cloudflare's published ranges](https://www.cloudflare.com/ips/) on 2026-10-29; review them if your proxy setup or those ranges change. [Cloudflare IP geolocation](https://developers.cloudflare.com/network/ip-geolocation/) must be enabled to supply country information.

The bundled world geometry uses public-domain [Natural Earth country data](https://www.naturalearthdata.com/about/terms-of-use/) at 1:110m scale, projected with Natural Earth 1. Small territories may only be visible in the country table. No external map tiles, API keys, or geolocation lookup service is required. To rebuild `world-map.json`, install the build-only tool with `npm install --prefix artifacts/tools/maps --no-package-lock --ignore-scripts d3-geo@3.1.1`, then run `node scripts/build-audience-map.mjs`; the script fetches a pinned dataset revision and emits its SHA-256.

## Analytics

The Analytics page follows the overview's header/navigation and includes current subscriber totals, Country/State/City breakdowns and a large country map, a subscriber chart with Today/This Week/This Month/Custom Dates filters, and a browser-family pie chart with its own date filters. Reloading, browser Back, and website switching retain the Analytics route; the original dashboard tab keeps its selected website. Geographic tables and map share one API response. State rows include their country; city rows include their state and country so identical city names in different states remain separate. Each geographic level reports its own unknown count, and located plus unknown equals the total. The tabs support arrow keys, Home and End.

The Subscribers panel uses a daily orange Total Subs line, date grid, a color-coded series legend, and a period summary alongside the chart. Hover over the plot or focus it and use Left/Right, Home, or End to inspect a daily count. Select Total Subs in the legend to hide/show it. Green desktop and blue mobile series are enabled when device metadata is available for that period, with independent legend toggles. Native-app and unsubscribe series stay disabled and labeled as not recorded; they are not plotted as zero. The total line counts additions among currently saved records, rather than lifetime subscribers. On narrow screens the legend wraps and the summary moves below the plot.

Authenticated `GET /api/domains/:key/analytics?start=YYYY-MM-DD&end=YYYY-MM-DD` returns a zero-filled daily series from currently saved, complete subscription records. Dates are UTC, include both endpoints, use Monday week starts in the UI, and span at most 366 days up to today. SQL groups TIMESTAMP values by UTC epoch day, independently of the database session time zone. The default range is the current UTC month through today. This is a read-only feature and needs no schema migration.

Subscriptions removed from the database no longer appear in this series: it represents saved records created during the selected period, not a complete signup/unsubscribe event history. Unsubscribe/net changes, native-app counts, and historical browser changes are not recorded and appear as unavailable rather than sample counts or zeros. Geographic breakdowns describe all currently saved subscriptions and are independent of the subscriber chart's date filter. Date filters do not send notifications or change subscriptions.

The API records an approximate `desktop` or `mobile` category on each new or resaved subscription, using the browser request headers (including the low-entropy mobile client hint where available). Tablets count as mobile browsers. It stores only nullable `subscriptions.device_type VARCHAR(16)`, never the raw User-Agent. Missing or unrecognized metadata preserves a previously known category; it does not classify old rows as desktop. See [MDN on the mobile hint](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-CH-UA-Mobile) and [User-Agent limitations](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Browser_detection_using_the_user_agent). Device categories are approximate and do not alter notification behavior.

Existing subscriptions acquire this category when their already-subscribed browsers revisit the website; the existing SDK resaves them automatically, without a plugin reinstall. Click Refresh data afterward. In each date period, desktop plus mobile plus device-unknown equals the saved additions. A mixed period shows recorded counts and explicitly explains unknown records; a period with only unknown devices shows unavailable splits. Empty periods have real zero counts. Device type describes the saved browser record, not a complete historical record of hardware changes.

Audience Browser Analytic uses a raised pie chart, callout percentages and a color-coded legend. Hover a slice or focus/select its legend item for the count and share. Chrome, Firefox, Edge and Safari keep consistent colors; Opera, Samsung Internet, Brave and Other appear when detected. Unknown browser records form a gray slice and remain in the percentage denominator. A period with no subscriptions shows an empty state, not an invented distribution. Native-app subscriptions remain untracked. On mobile, the pie stays centered and the legend provides the labels and percentages below it.

Startup adds nullable `subscriptions.browser_family VARCHAR(32)` storage. New and reconnecting subscriptions save a browser family from request User-Agent and supported [browser-brand client hints](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-CH-UA); the raw headers and browser versions are not stored. Detection checks Edge/Opera and other derivatives before Chrome/Safari compatibility tokens. Unknown requests preserve a previously recorded family. No plugin reinstall is required: old records populate as their subscribed browsers revisit. The authenticated date API returns browser counts and daily/device counts from the same grouped SQL result, scoped to the same owner, website, encryption-key requirements and UTC date range. Browser families describe the saved record, not a complete browser-change history.

## Push composer

The header's **Push Notification** menu opens `/push?domain=DOMAIN_KEY` in a new tab with the existing browser login, leaving the original dashboard open. Send Push quick links use the same composer in the current tab. Direct URLs, reload and browser Back restore the composer route. **New Push** opens Step 2 with a URL, title (150 characters), message (1000 characters), optional public HTTPS icon URL, emoji picker, and live Windows/MacOS/Mobile previews. Back preserves the draft within this page. Title, message, and notification URL are not saved across reloads; icon and explicitly saved banner defaults are. Notification appearance varies by browser; clicking the actual notification opens the URL.

Step 3 selects owned websites, web subscribers, All/Mobile/Desktop, and All/Yesterday/7 days/15 days/1 month. Yesterday is the previous UTC calendar day; the other windows are the last 7/15/30 rolling days. Platform filters include only recorded matching device types, with unknown exclusions explained. The authenticated read-only `/api/domains/:key/send-audience` endpoint counts complete subscriptions using the same scope and filter builder as the sending endpoint. Counts can change before send as subscriptions change.

Only **Send Push Now** posts to `/api/notifications/compose`, once per selected website. This dedicated URL requires explicit audience filters and fails closed against older API versions, which could otherwise ignore filters on the legacy endpoint. The server validates filters and selects only complete subscriptions belonging to that website and owner. Unsupported filters are rejected rather than falling back to All. The old WordPress sender and Configuration test form omit `audience` and keep their default All behavior. For multiple websites, use a relative URL so each target resolves on its own registered hostname. All selected links are validated before sending. The server sends the validated path/query/fragment to the installed worker so article links work on both apex and www subscriber origins without a plugin reinstall.

The UI reports push-service acceptance/failure/expired-removal results separately per website. It blocks repeated clicks while sending, does not retry ambiguous network failures automatically, and requires starting another notification after a send attempt. Tests use a stub push service; deployment checks only read audience counts/defaults and never send live notifications. Sending remains synchronous with bounded concurrency, so large campaigns still need a background queue. Templates, URL import, scheduling, custom segments and native-app audiences remain unavailable.

### Icon and banner defaults

The icon URL saves automatically after editing (or leaving the field), and Next waits for a successful save. Reset saves the ordinary bell default. Each website has its own defaults, shared across browsers through authenticated GET/PATCH `/api/domains/:key/push-defaults`. An additive startup migration creates nullable `domains.push_defaults JSON`; atomic JSON_SET updates keep icon and banner preferences independent. These changes preserve domain/VAPID keys and subscriptions. Saving defaults never sends a notification. Enter your existing icon URL once after upgrading.

Enable **Banner Settings** to enter an optional public HTTPS image URL or upload PNG/JPEG/WebP up to 5 MB. The browser resizes/re-encodes uploads as PNG (up to 1200 × 800, 512 KB output). Authenticated POST `/api/domains/:key/push-images` validates PNG structure, dimensions, and bounded decompression; SVG/HTML and oversized images are rejected. An additive `push_images` table stores immutable, content-addressed PNGs served publicly from `/api/push-images/:key/:hash.png`. The API never fetches arbitrary image URLs. Full database backups include uploaded images and preferences; deleting a website also removes its stored uploads. Images are retained until website deletion so existing notification links remain valid.

Add up to two buttons, each with a label and an optional website URL (blank follows the notification link). The sharing/call control offers Facebook, X, WhatsApp, and `tel:+COUNTRYNUMBER` actions. Ordinary and shared page URLs must belong to the selected website; relative paths work across multiple selected websites. Phone handlers depend on the device and can fall back to the notification page. Choose **Set above values as default**, then Next, to persist the current banner for the website whose composer is open; other selected audience websites do not have their defaults overwritten. To clear a saved banner, disable it, select the default checkbox, and click Next.

The server validates the image/actions and bounds the complete UTF-8 payload to 3500 bytes before sending; shorten messages or links if that limit is exceeded. The preview shows the current image and labels. Supported workers pass `image` and `actions` to showNotification and use notificationclick's action identifier to open the correct destination. Unsupported rich options fall back to an ordinary notification. Browser/OS support varies; the preview does not guarantee native appearance ([Notifications API reference](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)).

**Existing WordPress sites must update to plugin v1.2.0 for banners/buttons:** download the ZIP from Configuration or the composer, use Plugins → Add New Plugin → Upload Plugin, select the ZIP, and choose Replace current with uploaded. Keep the existing API/domain/VAPID settings; do not uninstall/delete the plugin or reset subscriptions. Revisit the website in each subscribed browser to allow its worker to update. Script installations should replace their hosted `push-sw.js`. Ordinary pushes remain compatible with older workers but their banner/actions are ignored. The backend/dashboard deployment alone cannot replace files in the separate WordPress installation.

## Website settings

Open **Settings** from the overview or settings navigation, or use `/settings?domain=DOMAIN_KEY`. The General Setting card saves the selected website's time zone through authenticated `GET`/`PUT /api/domains/:key/settings` endpoints. New domains also save the time zone selected during setup. Overview timestamps use the saved time zone; the default for existing websites is `Asia/Kolkata`. On startup, the API adds a nullable `domains.time_zone` column if necessary, preserving all existing keys and subscription records. Database backups include the preference.

Push Sending Settings displays the current domain key, a masked sender API key, and the VAPID public key. Private VAPID keys remain on the server; the card links to Configuration rather than replacing keys. Native iOS/Android push, email notifications/reports, SMTP, and Mailchimp are not implemented. Their reference-style cards and controls are disabled and do not save credentials, accept uploads, download a native SDK, or send test email.

## PWA settings

The **PWA Setting** tab at `/settings/pwa?domain=DOMAIN_KEY` uses the shared settings layout and saves a separate app name, short name, HTTPS start URL, colors, and two PNG icons for each website. The phone previews update as you edit and illustrate the install flow; actual prompts depend on the browser. Required icons are exactly 192x192 and 512x512 pixels, non-interlaced PNGs up to 512 KB each. The API validates dimensions, compressed and inflated sizes, names, colors, and the start URL's website hostname (including its `www` equivalent).

Authenticated `GET`/`PUT /api/domains/:key/pwa` endpoints read and save the form. Startup adds nullable `domains.pwa_settings JSON` storage without modifying push keys or subscriptions; full database backups include the settings and icon bytes. Public `/api/pwa/:key/icon-192.png` and `icon-512.png` endpoints serve only saved app icons with PNG content types. JSON uploads have a larger bounded limit only for this form; other routes keep their existing request limit.

After saving, download `push-pwa-manifest.json`, upload it to the website root, and add `<link rel="manifest" href="/push-pwa-manifest.json">` to the website's HTML head. Replace that file after changing PWA settings. Its icons point to the API's public icon URLs, so keep the API accessible and allow it in any website image CSP. The manifest uses standalone display and a website-root scope. This dashboard does not automatically change WordPress or provide offline page caching. WordPress installations should keep the plugin's existing worker; the optional `push-sw.js` download is the existing notification worker, not a second worker to register over it.

## Administrator account

The **Account** tab at `/settings/account` displays the actual administrator username (or email when the login uses an email address), account status, and the most recent successful login recorded by the API. Login history starts with this feature; older logins show **Not recorded yet**. Connection IP is the address seen by the API socket and may be a reverse proxy address; untrusted forwarded headers do not overwrite it. Dates use the selected website's time zone when available. The avatar is a generic local illustration, and deletion of the sole administrator is disabled.

Change Password requires the current password and a different replacement of 12–128 characters. Passwords are stored as salted scrypt hashes in a new `admin_accounts` table, initialized once at API startup from `ADMIN_USERNAME` and `ADMIN_PASSWORD`. Those environment values are bootstrap credentials: subsequent restarts and deployments preserve the stored account and password. Update the password through Account after initialization. A password change returns a replacement session for the current browser and invalidates older dashboard sessions, including legacy sessions. Website VAPID keys and WordPress sender API keys remain unchanged.

Backups now dump the entire dedicated project database, including `admin_accounts`. Deployment checks use an internal short-lived signed session and the current database session version, so a password change does not require putting the new password in GitHub or changing deployment secrets. The deployment probe does not overwrite human login history. The production entry point always uses the MySQL account repository; an injectable in-memory repository is available for isolated HTTP tests.

### Repair an installation from an older ZIP

Version 1.1.0 archives built by Windows PowerShell could contain literal backslashes in ZIP paths. Linux hosting can extract these as filenames such as `push-notifications-plugin\push-notifications.php` instead of creating a directory. WordPress then generates an activation path that does not exist.

Version 1.1.1 fixes the packager to write forward slashes explicitly. Remove the failed inactive installation and upload the newly rebuilt ZIP. If WordPress cannot remove the failed installation, use your hosting File Manager to remove only the failed `wp-content/plugins/push-notifications-plugin` folder, then reinstall. The final main file must be `wp-content/plugins/push-notifications-plugin/push-notifications.php`, with all three plugin files directly inside that folder. The test suite checks the raw local and central ZIP header names to catch separator problems without Windows path normalization hiding them.

## Validation and packaging

For Hostinger KVM with an existing Docker/Caddy setup, use the separate Compose project in `deploy/hostinger`. It includes production API/dashboard images, a private persistent MySQL database, and routing through the existing Caddy service. See [Hostinger deployment](deploy/hostinger/DEPLOYMENT.md) for configuration, migrating the Cloudways database and keys, and the coordinated DNS cutover.

For automatic Hostinger updates after pushing to `main`, see [GitHub Actions setup](deploy/hostinger/AUTO-DEPLOY.md). The workflow tests changes, uses a dedicated restricted SSH key, backs up data, builds and checks the app containers, and attempts image rollback on a failed cutover. Complete the one-time server/key/secrets setup before expecting automatic deployments.

For Cloudways Flexible, use `powershell -ExecutionPolicy Bypass -File scripts/package-cloudways.ps1` to create `artifacts/push-api-cloudways.zip`. The application SFTP root can be protected; upload into `private_html`. The ZIP includes PM2 configuration and proxy rules for a separate API application. See `deploy/cloudways/DEPLOYMENT.txt` for the SSH, database, HTTPS, and Cloudways support prerequisites. Cloudways does not use the cPanel Application Manager procedure below.

For cPanel Application Manager, run `powershell -ExecutionPolicy Bypass -File scripts/package-cpanel.ps1`. This creates `artifacts/push-api-cpanel.zip` with a CommonJS `app.js` wrapper for Passenger, the backend, and public SDK/plugin assets. It excludes credentials and dependencies. Upload it to the hosting home directory and extract it to create `push-api`. Full instructions are in `deploy/cpanel/DEPLOYMENT.txt`. Register the app with path `push-api`, a dedicated API subdomain, and production environment variables; use Enable Dependencies to install the root package's dependencies.

- `cd server; npm.cmd test`: HTTP route, authentication, subscription, notification delivery, SDK permission, and service worker tests. External push services are mocked.
- `cd client; npm.cmd run build`: frontend build.
- `cd client; npm.cmd test -- --watchAll=false --runInBand`: overview counts, navigation, refresh/retry states, and domain-card interactions.
- `C:\xampp\php\php.exe -l wordpress/push-notifications-plugin/push-notifications.php`: PHP syntax check (or use your installed PHP).
- `C:\xampp\php\php.exe wordpress/test-plugin.php`: WordPress API contract checks with stubs.
- `powershell -ExecutionPolicy Bypass -File scripts/package-wordpress.ps1`: copy the current worker into the plugin and rebuild the downloadable ZIP from `wordpress/push-notifications-plugin`.

Sending is synchronous with bounded concurrency, suited to initial testing and small audiences. Larger campaigns need a background queue. This remains a single-admin application; user registration, domain ownership verification, campaign scheduling, and analytics are separate unfinished features.
